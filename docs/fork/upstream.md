## Получение обновлений

Начинай с чистого рабочего дерева; сохраняй незавершённые изменения без перезаписи чужой работы.
Пример для новой ветки интеграции (имя выбирается под конкретное обновление):

```powershell
git fetch upstream
git switch -c chore/upstream-sync main
git log --oneline HEAD..upstream/main
git merge upstream/main
```

Разреши конфликты, проверь миграции, `package.json`/lockfile, изменения инструкций и workflow.
Выполни `npm ci` и интеграционные проверки из [development.md](development.md).
После проверки обнови исходную точку в этом документе и передай изменения в `origin` обычным PR.
Не применяй force-push для синхронизации и не сбрасывай форк на upstream.

## Перед первым собственным релизом

Унаследованные publish workflows, Docker image names, badges и ссылки на приложения могут вести к оригиналу.
Проверь назначения в [docker-publish.yml](../../.github/workflows/docker-publish.yml),
[stable-branch.yml](../../.github/workflows/stable-branch.yml) и [releases.md](../releases.md).
Не запускай выпуск до настройки собственных адресов и проверки совместимости клиента.
Версии upstream — `x.y.z`; beta/stable задаётся GitHub prerelease flag.
При активном beta-канале публикуй с `--prerelease`, без `--latest`; promotion требует запроса владельца.
