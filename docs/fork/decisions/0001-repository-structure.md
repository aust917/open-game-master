# ADR 0001: структура форка и контекст агентов

Статус: принято. Дата: 2026-10-28.

## Контекст

Нужен русский интерактивный D&D-мастер. Open Game Master уже содержит приложение,
серверный игровой движок, LLM-интеграции, тесты и большой объём документации.
Агентам нужен быстрый доступ к конкретной подсистеме без загрузки всех планов и аудитов.

## Решение

- Сохраняем расположение исходников, скриптов и assets upstream; не вводим искусственный монорепозиторий.
- `AGENTS.md` — краткий маршрутизатор и общие инварианты. Вложенные инструкции содержат только особенности области.
- `docs/fork/` — цель, текущий план, карта кода, workflow и решения форка. Старые документы upstream остаются на своих местах.
- Каждое знание имеет одного владельца: фактическое поведение — код/тесты, приоритеты — roadmap,
  архитектурные причины — ADR, рабочее состояние сложной задачи — её task-файл.
- `CLAUDE.md` и Copilot adapter отсылают к общим инструкциям. Не размножаем независимые наборы правил.
- Проверяем объём входных инструкций и ссылки автоматически без установки зависимостей приложения.

## Последствия

Обновления из upstream дают меньший diff; перевод интерфейса и улучшение рассказчика можно делать по отдельности.
Карта требует обновления при изменении границ. Агент выбирает документы по задаче, а не читает их все.
Пустые каталоги под будущую архитектуру и skills «на всякий случай» не создаём.
Реальные повторяющиеся workflows можно выделить позже, когда появятся наблюдаемые ошибки или затраты.

## Отклонённые варианты

Перенос существующего кода в `apps/` и `packages/` без функциональной необходимости усложняет upstream merges.
Один большой файл с документацией и историей увеличивает стартовый контекст и быстро устаревает.
Копии общих правил для каждого инструмента расходятся при редактировании.

Обоснование практик и первичные источники: [agent-practices.md](../agent-practices.md).
